# LaminaDB 可重建查询工作负载语料 — 设计与取舍

本目录交付一套**可重建**的查询工作负载语料，供后续规划器（access path /
candidate 选择）做有历史纵深的比较，避免被"当前快照上的静态小数据"误导。

语料不是随机文件集合，也不包含规划器实现。它由四类工件构成：

| 子目录 | 内容 | 如何重建 |
| --- | --- | --- |
| `scenarios/` | 输入生成材料：每个实例的确定性生成声明（seed + 轨迹族 + 形状参数）、操作脚本（将被 HTTP 重放的事务序列）、查询清单 | `python3 -I tools/build_scenarios.py` |
| `answers/` | **独立答案**：由 `tools/reference_model.py` 仅消费操作脚本与 vacuum 水位推导，不接触 laminad 二进制 | `python3 -I tools/reference_model.py` |
| `runs/` | **运行事实**：真实 laminad 实例重放同一脚本后返回的逐查询结果与 plan 事实、vacuum 前后统计、410 观测 | `python3 -I tools/run_corpus.py` |
| `tools/` | 全部生成/推导/执行/核对脚本（仅 Python 3 标准库） | — |
| `report/` | 方案比较实验、覆盖矩阵与预算代价说明 | 由脚本生成 `report/*.json`，结论见本文件 |

所有脚本以 `python3 -I` 运行，不依赖工作目录中的模块；脚本与数据分离，
laminad 数据目录全部位于系统临时目录下的全新空目录。

## 1. 为什么静态最终行不够（语料的核心机制）

LaminaDB 的历史答案由两件独立维护的东西共同决定：

1. **事务提交维护的版本链**：每个主键持有按提交序号排列的 `Version{seq, row|tombstone}`，
   快照 `at` 的可见行是链上 `seq <= at` 的最后一个版本，墓碑视为不可见
   （对应 `internal/versions/store.go: Visible`）。
2. **独立回收维护的可读水位**：`POST /vacuum {horizon}` 实际水位取请求值与所有活动事务
   快照的最小值；每条链保留水位时刻的最后版本 + 之后的全部更新；水位前的最终墓碑整条删除
   （对应 `internal/versions/vacuum.go` 与 `engine/maintenance.go`）。水位单调不回退，
   `at < horizon` 的按序号查询返回 410。

因此同一份"最终行"在两个实例上可以对应完全不同的历史答案。语料显式构造
**当前分布相同、更新轨迹不同**的实例对（scenario 族 `trajectory_a` / `trajectory_b`），
并在多个目标快照上独立推导答案，而不是只保存 head 行。

索引使差异进一步放大：二级索引保留**历史非空值 → 主键**的候选超集
（`internal/index`），规划器选择候选键最少的索引，但候选必须回到指定快照的真实版本
重新做残余判断。于是 `plan.candidates`（历史超集大小）、`scanned`（可见且进入残余
判断的行数）、`matched`（限制输出前的匹配数）是三个不同的量；过度更新的实例会出现
candidates 远大于 scanned 的"索引膨胀"，只看 head 分布无法区分。

## 2. 判别力维度（必须覆盖的四类情形）

1. **同分布、异轨迹实例对**：head 快照的行多重集合逐字节相同，但版本链长度/中间值不同。
   判别点：历史快照答案不同；索引 candidates 不同；vacuum 移除版本数不同。
2. **低选择性谓词**：命中比例高（如 `valid = true`、宽区间 `amplitude >= 10`），
   索引路径候选数 ≈ 全表，规划器若只比候选数会在 scan/index 间摇摆。
3. **高重复值**：谓词列只有少数取值（布尔、小基数文本），等值谓词命中大量主键，
   配合唯一/非唯一索引观察候选去重与残余判断。
4. **水位与可查询性**：活动事务钉住水位（`pinned=true`）、关闭读者后推进、
   被淘汰快照 410、vacuum 后索引重建、checkpoint/重启后水位仍有效。

## 3. 预算问题与方案比较（实际比较，而非拍脑袋）

"展开全部历史组合" = 实例 × 轨迹 × 快照 × 谓词 × 排序 × limit 的笛卡尔积，
样本数随版本链长度组合爆炸；"每个实例只留 head 一行"则让错误解释（例如忽略墓碑、
忽略水位、把索引候选当最终行）轻松通过。

`tools/selection_experiment.py` 在候选池上实测三种选择方案，指标与原始数字见
`report/selection_report.json`（当前实测）：

- **方案 A 全量展开（48 查询 / 9584B，66/66 故障签名）**：判别力与成本上限，
  作为对照基线，不按此预算交付。
- **方案 B 每实例单 head 样本（6 查询 / 1024B，仅 25/66 ≈ 38% 签名）**：最省预算，
  但忽略墓碑、忽略水位、把候选当最终行、用 head 回答历史等错误解释在它上面大量漏网，
  实测证明过度精简不可接受。
- **方案 C 分层覆盖（交付，21 查询 / 4280B ≈ 全量 45%，66/66 = 100% 签名）**：
  按 (判别维度 × 谓词形态 × 快照角色) 分层，同分布异轨迹配对强制同时入选，
  410/墓碑/null/残余判断各占独立层，再按"每字节新增签名数"贪心补齐并保证
  稀有签名不被饿死。以约一半预算拿到与全量相同的故障签名覆盖率。

故障签名来自一个**变异解释器**（`tools/mutants.py`），它只作用于独立参考模型：
注入 6 类错误解释——忽略墓碑、忽略 vacuum 水位、把索引候选当最终行、用 head 值
回答历史快照、null 误匹配普通比较、索引路径跳过残余判断——检查语料答案能否区分。
当前 66 个维度化故障签名全部被交付语料杀死（见 `report/selection_report.json`）。

## 4. 独立性与可信链

```
 scenarios/*.json (生成声明, 固定 seed)
        │  build_scenarios.py（确定性，无随机种子外的随机源）
        ▼
 scenarios/*/script.json  ──► reference_model.py ──► answers/*.json
        │（HTTP 重放）                                   ▲ 不 import 任何 Go 代码
        ▼                                                │ 也不读取 runs/
 run_corpus.py → 真实 laminad（临时数据目录）            │
        │                                          verify_corpus.py 逐字段核对
        ▼                                                │
 runs/*.json  ───────────────────────────────────────────┘
```

- 参考模型是对公开语义（README/PROJECT_SPEC 描述 + 脚本输入）的独立 Python 实现，
  不读取 Go 源码路径、不读取运行结果；两者只在 `verify_corpus.py` 中碰面。
- 每个目标快照在答案中带 `queryable` 标志：参考模型依据推导出的水位判断，
  运行事实依据真实 HTTP 状态码（200 / 410）核对。
- 重建是幂等的：固定 seed 使场景字节级稳定；脚本重复执行产生相同 answers。

## 5. 明确的覆盖取舍（代价说明）

见 `report/coverage_matrix.md`（生成）。摘要：

- **放弃**：全笛卡尔展开（预算超限，见 selection_report 的字节数对比）、JOIN/GROUP BY
  等内核未实现的能力、串行化异常（产品只承诺快照隔离）。
- **保留**：四类判别维度每类至少一对实例与多快照查询；每个变异解释必须被杀死；
  每个实例至少一个 410 核对与一个 pinned vacuum 观测。
- **残余风险**：语料规模刻意保持在有界内存级别（默认每关系数百键、每链个位数版本），
  不能外推到容量极限行为；样本证明的是"区分力存在"，不是性能基准。
